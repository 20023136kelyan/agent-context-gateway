# Upper-bound experiment

Tests Bifröst's core premise before any of the product is built: **do the right
notes, shown to an agent at the place it is working, make it measurably better?**
It also tests whether a model can write those notes from another agent's work.

If hand-written notes delivered at the right place don't help, nothing
downstream (event pipeline, classification, the service) can rescue the idea,
and the project stops. The bar to continue, from the project README: **at least
15% faster or cheaper, or materially better completion of trap tasks.**

## The loop being tested

```text
seed run ──► trace + graded outcome ──► model writes notes ──► fresh agent gets the notes at the place ──► graded
(agent, no notes)                        (generate.ts)          (hook or MCP)
```

That is the whole product in miniature: one agent's work becomes knowledge that
helps the next one. Only the pieces the agent touches are built for real (hook,
MCP tool, notes format). Everything else is a script.

## Arms

| Arm | Notes | Delivery | Question it answers |
|---|---|---|---|
| `control` | none | hook installed, silent | Baseline. Same hook overhead as the other arms. |
| `none` | none | no hook | Does the hook itself change anything? (optional) |
| `hand` | hand-written | pushed on file reads and edits | **The ceiling: are notes worth anything at all?** |
| `wrong` | deliberately wrong | pushed | What does a bad note cost? |
| `hand-pull` | hand-written | MCP tool plus one instruction line | Does pull-only delivery (the Codex and Cursor fallback) work? |
| `gen:<file>` | generated by a model | pushed | Can a model write notes as good as a person? |
| `pull:<file>` | any notes file | MCP only | Pull-only with generated notes |

Generated arms, as planned in the study:

| Arm | Generator | Input |
|---|---|---|
| C `gen:gen-opus-full` | a strong model (default `claude-opus-5`) | full trace |
| D `gen:gen-open-full` | the open-weight model you would host | full trace |
| E `gen:gen-open-digest` | the same open-weight model | scrubbed digest only |

How to read the gaps:

- **hand ≈ control:** the premise fails. Stop.
- **C well below hand:** writing notes is the hard part.
- **D well below C:** the hosted model is the bottleneck.
- **E well below D:** the digest loses too much, which affects the privacy design.

## Layout

```text
experiments/upper-bound/
├── kit/                     what agents touch
│   ├── notes-lib.mjs        matching, ranking, budget, formatting
│   ├── hook.mjs             PreToolUse hook (push); ~70 ms, fails open, never blocks
│   ├── opencode-plugin.mjs  the same push logic for OpenCode (appends to tool results)
│   └── mcp-server.mjs       one tool, bifrost_at(path) (pull)
├── harness/
│   ├── run.ts               arms × tasks × reps; isolates, runs, grades, measures
│   ├── generate.ts          trace → model → notes file
│   ├── trace.ts             trace parsing, full and digest rendering, secret scrubbing
│   ├── report.ts            rates, deltas against control, bootstrap intervals, verdict
│   └── fake-agent.mjs       scripted agent for smoke-testing the plumbing (not data)
├── tasks/<id>/
│   ├── task.json            prompt, grader command, labels, signals
│   ├── repo/                what the agent gets
│   ├── hidden/              grader, copied in only after the agent finishes
│   ├── reference/           a correct fix and the naive fix, to validate the grader

```

## The first trap task: `refresh-rotation`

A small token-refresh client (`tokenbox`). The ticket asks to make token refresh
survive network blips. The obvious fix, retrying the refresh request, is wrong:

- the auth server rotates refresh tokens and revokes the whole token family when
  a used one is presented again;
- a timeout can happen *after* the server rotated;
- so a plain retry signs every device out.

The safe fix reuses one `Idempotency-Key` across the retries. Both facts are
written down, but only deep in `docs/vendor/authserver-api.md` (§10.2 and §11).
A careful agent can find them unaided; the `read vendor doc` column in the report
shows how often each arm did.

The hidden grader uses a faithful fake of the vendor server and injects faults
that lose either the request or the response. It reports:

| Field | Meaning |
|---|---|
| `visible` | the repo's own tests pass |
| `goal` | a lost request no longer signs the user out |
| `trapAvoided` | a lost response does not trigger reuse detection |
| `failFast` | a rejected refresh token is not retried |
| `pass` | all four |
| `trapHit` | goal met but trap not avoided: the naive fix |

The grader has been checked against both reference fixes: no fix fails `goal`,
the naive fix is a `trapHit`, and the correct fix passes (`tests/experiment-kit.test.ts`).

## Variants of the first task

The smoke test showed `refresh-rotation` is too easy: the repo is 5 files, so an
agent reads everything, including the vendor doc, and finds the answer unaided
(Muse Spark passed without notes). Two variants share its grader and fix the
problem in different ways:

| Task | What changes | What it tests |
|---|---|---|
| `refresh-rotation-undocumented` | The repo's copy of the vendor doc is v3.1, from before reuse detection and idempotency keys. The transport has no named idempotency option. Nothing in the repo says a retry is dangerous. | Do notes carry knowledge that exists only in past work? Control should fail almost always, by construction. |
| `refresh-rotation-buried` | A ~48-file repo. The vendor docs are split into 13 pages; rotation is one section of `security.md`, the header one entry in `request-headers.md`. Two lures point at a plain retry: the `withRetry` helper and ADR 0003. `Idempotency-Key` appears in the payments code, so it reads as a payments thing. | Do notes at the place beat an agent searching on its own? A careful agent can still find the answer. |

**Results, undocumented (Muse Spark 1.3, free, `xhigh`, 10 valid runs per arm):**

| Arm | Pass | Trap hit | Median time |
|---|---|---|---|
| control (no notes) | 0/10 | 5/10 | 177s |
| hand (correct notes) | 10/10 | 0/10 | 148s |
| wrong (misleading notes) | 0/10 | 0/10 | 111s |

Correct notes turn a task the model never solves into one it always solves.
Wrong notes are not neutral: the model follows them and fails every time. The
wrong arm is faster only because it fails sooner, so the report does not count
time or cost savings for an arm that never passes. Timings are rough: the free
model is rate-limited, and 5 runs that got no response were left out and re-run.
This variant separates the arms by construction, so it shows the most notes can
do, not how often an agent needs them.

**Buried variant:** it did not separate the arms (all 10 runs passed, across the 3 arms).
The model read ~40 of its 48 files and already knew refresh-token rotation from training, so control
passed every time. Hence a third variant:

| Task | What changes | What it tests |
|---|---|---|
| `refresh-rotation-vendor` | ~186 files (built by its `generate.py`). Keyline's safe retry is a proprietary `Keyline-Retry-Token` header and the standard `Idempotency-Key` is ignored, so the textbook fix is a trap too. The fact is in one section of `request-headers.md`; payments code uses `Idempotency-Key`. | Notes against search when the model's training points the wrong way, in a repo too large to read end to end. |

A task can point `repo` and `hidden` at another task and add `overlay` (files
copied over the repo) and `remove` (paths deleted), so variants don't copy the
grader. The kit tests check that each grader separates no fix, the naive retry
and the correct fix. They also check that nothing in the undocumented repo
mentions the trap.

## Protocol

Two runners are verified: **Claude Code** and **OpenCode**. OpenCode is the cheap
path: it runs on whatever provider and model you already use (OpenRouter, DeepSeek,
a local server…), so a run costs what that model costs. Use the same model in every arm.

### With OpenCode

The OpenCode runner has been checked end to end against the real `opencode` binary
(1.18) with a scripted mock model. That covered:

- the plugin loading;
- notes reaching the model;
- the MCP pull tool;
- the trace, cost and grading.

It has not yet been run with a real model.

- **Push arms** load `kit/opencode-plugin.mjs`, which appends the notes to the
  result of the tool call that touched the place. OpenCode can't add context
  *before* a tool runs, so the agent sees a warning just after reading the file.
  That is early enough, because agents read before they edit.
- **Pull arms** get the `bifrost_at` MCP tool and one instruction line.
- **Config** goes in through `OPENCODE_CONFIG_CONTENT`, on top of your own
  OpenCode config (providers, keys). Nothing is written into the workspace.
- **Permissions:** edits and shell are allowed without prompts, and files outside
  the workspace are denied.
- **No per-run spending cap.** OpenCode has no `--max-budget-usd`, so only
  `--timeout-min` limits a run. Check the smoke test's cost before a batch.

```bash
# 1. smoke test, one run per arm (model is provider/model, as in `opencode models`)
npm run exp:run -- --agent opencode --model <provider/model> --tasks refresh-rotation --arms control,hand --reps 1 --keep
# 2. the ceiling
npm run exp:run -- --agent opencode --model <provider/model> --tasks refresh-rotation --arms control,hand,wrong --reps 10
npm run exp:report -- experiments/upper-bound/results/<stamp>
```

The generator also works with OpenRouter or any OpenAI-compatible provider:
`OPENAI_BASE_URL=https://openrouter.ai/api/v1 OPENAI_API_KEY=… npm run exp:generate -- --provider openai --model <model> …`.

The steps below use Claude Code. Add `--agent opencode --model <provider/model>` to
run any of them with OpenCode.

### With Claude Code

Claude Code must be installed and logged in (Codex too, for its pull arms). Runs
use your own account and cost real money; `--budget-usd` caps each run.

**1. Smoke test with a real agent (one rep).** Check that the hook fires and the
grader runs:

```bash
npm run exp:run -- --tasks refresh-rotation --arms control,hand --reps 1 --budget-usd 3 --keep
```

Then look in `results/<stamp>/refresh-rotation/hand/rep-01/`:

- `deliveries.jsonl` should show `rr-1` and `rr-2` delivered;
- `grade.json` holds the result;
- `diff.patch` holds what the agent changed.

**2. The ceiling: control against hand-written notes.**

```bash
npm run exp:run -- --tasks refresh-rotation --arms control,hand,wrong --reps 10 --budget-usd 3
npm run exp:report -- experiments/upper-bound/results/<stamp>
```

Use at least 10 runs per arm. With fewer, the intervals are too wide to decide
anything. If `hand` doesn't beat `control`, stop here.

**3. Generate notes from seed runs.** Control runs double as seed runs: each
trace ends with the graded outcome, as a later test run or incident would show
it. Pick one control trace in which the agent fell into the trap, then:

```bash
# C: strong model, full trace (needs ANTHROPIC_API_KEY or `ant auth login`)
npm run exp:generate -- --task refresh-rotation --trace <control trace.jsonl> \
  --provider anthropic --input full --out experiments/upper-bound/tasks/refresh-rotation/notes/gen-opus-full.json

# D and E: open-weight model on an OpenAI-compatible server (vLLM, llama.cpp, SGLang, hosted)
OPENAI_BASE_URL=http://localhost:8000/v1 npm run exp:generate -- --task refresh-rotation --trace <same trace> \
  --provider openai --model <model> --input full --out experiments/upper-bound/tasks/refresh-rotation/notes/gen-open-full.json
OPENAI_BASE_URL=... npm run exp:generate -- ... --input digest --out .../notes/gen-open-digest.json
```

Read the generated files before using them. Each lists what it dropped: paths
not in the repo, and text cut to 280 characters.

The Anthropic call uses structured JSON output, adaptive thinking and
**server-side refusal fallbacks (`fallbacks: "default"`)**. If the model
declines, the API retries on a fallback model instead of failing the run.
Remove it in `generate.ts` if you'd rather see refusals.

**4. Test the generated notes.**

```bash
npm run exp:run -- --tasks refresh-rotation --arms control,hand,gen:gen-opus-full,gen:gen-open-full,gen:gen-open-digest --reps 10
```

Keep `control` and `hand` in every batch, so all arms share the same conditions.

**5. Pull-only delivery.**

```bash
npm run exp:run -- --tasks refresh-rotation --arms control,hand-pull --reps 10
npm run exp:run -- --agent codex --tasks refresh-rotation --arms control,hand-pull --reps 10   # runner unverified
```

## Harness options

| Option | Default | Meaning |
|---|---|---|
| `--tasks` | required | Comma-separated task ids |
| `--arms` | `control,hand` | Built-in arms, `gen:<file>` or `pull:<file>` |
| `--reps` | 10 | Runs per task and arm |
| `--agent` | `claude` | `claude`, `opencode`, `codex` (unverified) or `command` |
| `--model` | agent default | Pinned model; use the same for every arm |
| `--budget-usd` | none | Per-run spending cap (Claude Code `--max-budget-usd`; ignored by OpenCode) |
| `--timeout-min` | 20 | Per-run wall-clock limit |
| `--idle-min` | 6 | Stop a run after this long with no agent output (a stalled model); it is marked invalid. `0` turns it off |
| `--concurrency` | 2 | Parallel runs |
| `--setting-sources` | `project` | Which Claude Code settings load. `project` keeps your user hooks and CLAUDE.md out of the runs. |
| `--cooldown-sec` | 0 | Pause after an invalid run before starting the next (rate-limited free models) |
| `--resume` | off | With `--out <dir>`: keep that batch's valid runs, re-run the missing and invalid ones |
| `--keep` | off | Keep each run's workspace for inspection |
| `-- <args>` | | Extra arguments passed to the agent |

## What keeps it fair

- **Isolated workspaces.** Every run gets a fresh copy of the task repo in a temp
  directory, outside this repository, as its own git repo. The notes, the grader
  and the reference fixes are not in it. The grader is copied in only after the
  agent exits.
- **Same conditions per arm.** Every arm starts the agent the same way:
  - the same prompt and model;
  - `--setting-sources project`, `--strict-mcp-config` and no session persistence;
  - `control` has the same hook installed as the notes arms, only silent.
- **Interleaved order.** Runs cycle through the arms rep by rep, so rate limits or
  model updates during a batch hit every arm alike.
- **Everything recorded.** Each run keeps its trace, deliveries log, diff, grade and
  metrics, so any result can be checked by hand.

## Known limits

- **One task.** A credible result needs 10 or more trap tasks across different
  kinds of knowledge: vendor constraints, past decisions, flaky areas, in-progress
  work. Copy `tasks/refresh-rotation` as the template. Each task needs:
  - a hidden grader that separates "goal met" from "trap hit";
  - reference fixes that prove it does.
- **Seed traces carry the grader's explanation.** The outcome appended to a trace
  includes why the trap failed, as a post-incident note would. The generated arms
  therefore test *distilling* knowledge from work plus outcome, not discovering it.
  That matches how Bifröst would learn in practice (work history plus what
  happened after), but should be stated with the results.
- **The trap repeats exactly.** The seed task and the test task are the same task.
  Related-but-different tasks, where a note must transfer, belong in the next round.
- **Agents with unrestricted file access could find the task files.** A thorough
  agent could search the filesystem and find `experiments/`. Check `readPaths` in
  `result.json` if a result looks too good.
- **Invalid runs.** A run is invalid, not failed, when the agent never started (network, auth, model
  name) or when it hit the timeout after going silent for 5+ minutes (a stalled model connection;
  free hosted models do this). The report leaves invalid runs out; `--resume` re-runs them.
- **Not yet run against real agents.** The plumbing is tested with the scripted
  agent, and with real OpenCode driven by a scripted mock model. The first real step is the one-rep smoke test above, run on your
  own machine: in the cloud dev container the runs execute as root, Claude Code
  refuses `bypassPermissions` there, and the headless runs need it.
- **The Codex runner is untested.** Its flags follow `codex exec` as documented;
  verify on first use. Push delivery is not offered for Codex (see the study,
  §7.1 of `docs/study/bifrost-on-maps.md`).
- **Running as root:** Claude Code refuses `bypassPermissions` for root. Run as
  a normal user.
- **Your global agent config loads in every arm.** Claude Code runs load project
  settings only. OpenCode runs still load your global OpenCode config (for providers
  and keys), including any global AGENTS.md or plugins; they skip `~/.claude`. That's
  the same in every arm, but keep your global instructions short while running it.
